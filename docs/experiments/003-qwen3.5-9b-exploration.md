# 003: Qwen3.5:9b exploration (local Ollama, thinking disabled)

- Date: 2026-11-07
- Command: `uv run python scripts/run_k_sweep.py --k-values 40,50` (local
  Ollama, V100 32GB), after `think: default true` was disabled per
  [decisions/0016](../decisions/0016-disable-ollama-thinking-mode.md).
- Pipeline: `src/amem_gepa/paper_repro.py`, via
  `external/agentic-memory-repro` (`WujiangXu/AgenticMemory`), per
  [decisions/0013](../decisions/0013-paper-reproduction-pipeline.md).
- `PAPER_REPRO_BACKEND=ollama`, `PAPER_REPRO_MODEL=qwen3.5:9b`. Full
  10-conversation dataset, n=1986 questions.

## What this is, and isn't

**This is exploration, not reproduction.** Qwen 3.5 is not one of the
paper's six originally-benchmarked models (GPT-4o-mini, GPT-4o,
Qwen2.5-1.5b/3b, Llama-3.2-1b/3b —
[decisions/0013](../decisions/0013-paper-reproduction-pipeline.md),
`PAPER_CATEGORY_K`), so there's no known "correct" per-category `k` to
splice against (unlike
[002](002-m2-gpt4o-mini-reproduction.md)'s GPT-4o-mini result) and no
paper row to check this against directly. `k=40` and `k=50` were swept
uniformly across the whole dataset; `k=40` won on overall F1 and is what's
reported below, as a single uniform-`k` run, not a per-category splice.

## What changed vs. the previous experiments

This is the result of a genuinely long diagnosis, now resolved:

1. A local `qwen3.5:9b` sweep on an 8GB RTX 3070 took >15 days for just
   `k=40,50` -- diagnosed via `ollama ps`/`nvidia-smi` as likely VRAM/CPU
   offload.
2. Upgrading to a 32GB V100 didn't fix it (3+ days, still unfinished) --
   `ollama ps` showed `100% GPU`, `nvidia-smi` showed 77% utilization
   during an active call, and an isolated benchmark showed a healthy
   72.92 tok/s. Hardware was never actually the problem.
3. Added progress/ETA/diagnosis logging to `paper_repro.py`
   (`_ProgressTracker`, `_patch_ollama_chat`'s per-call timing + content
   preview capture) -- real logs showed steady ~73 tok/s and
   `unaccounted=0.0s` throughout, but 1,200-15,000+ tokens generated per
   turn for what should be short structured outputs.
4. `ollama show qwen3.5:9b` found the actual cause: `thinking: default
   true`. A live comparison: default used 1,115 eval tokens/15.3s for a
   short keyword-extraction call; `think=False` used 11 eval tokens/0.1s
   with a functionally identical answer.
5. Fixed in [decisions/0016](../decisions/0016-disable-ollama-thinking-mode.md):
   `_patch_ollama_chat` now injects `think=False` into every Ollama call
   this pipeline makes. This run is the first full, completed result with
   that fix in place.

## Comparison against the other two models already run through this pipeline

Not a paper comparison (no paper row exists for this model) -- this is
just situating `qwen3.5:9b` against
[001](001-m2-llama3.2-1b-full-reproduction.md)'s Llama-3.2:1b (`k=10`,
per the paper's own Table 8 config for that model) and
[002](002-m2-gpt4o-mini-reproduction.md)'s GPT-4o-mini (spliced
per-category `k` per Table 8), all through this exact pipeline. F1,
0-100 scale:

| category    | Llama-3.2:1b | GPT-4o-mini | Qwen3.5:9b |
|-------------|--------------|-------------|------------|
| multi_hop   | 16.66        | 27.07       | **34.99**  |
| temporal    | 9.27         | **43.67**   | 39.59      |
| open_domain | 8.70         | **15.10**   | 13.13      |
| single_hop  | 24.83        | 43.58       | **51.86**  |
| adversarial | 35.24        | **56.31**   | 54.52      |

`qwen3.5:9b` leads on multi_hop and single_hop, and is within a few
points of GPT-4o-mini (never the lowest of the three) on the rest --
consistent with it being a newer, larger (9B dense) model than either,
even with thinking disabled. Take this as a rough, exploratory signal,
not a rigorous comparison: the three runs used different `k` selection
methodologies (Llama/GPT-4o-mini follow the paper's own per-model/
per-category config exactly; Qwen used whichever uniform `k` scored best
in a 2-value sweep, not a paper-sanctioned choice).

## Cost

Local Ollama (`qwen3.5:9b`), $0 API cost. **Wall-clock: ~24 hours** for
the full `k=40,50` sweep -- a dramatic improvement over every pre-fix
attempt (>15 days on the RTX 3070 for the same two `k` values; still 3+
days and unfinished on the V100 before `think=False`). Exact composition
(whether this includes a fresh memory-build pass, i.e. whether the
`qwen3.5:9b` cache was cleared first per
[decisions/0016](../decisions/0016-disable-ollama-thinking-mode.md)'s
recommendation, or reused memories built under the old thinking-on
behavior) isn't confirmed -- see that same ADR's note on why mixing
thinking-mode memories with non-thinking QA-answering would be a real
methodological inconsistency, not just a cost question. Back-of-envelope
sanity check either way: ~24h implies roughly 4-11s/call on average
(depending on whether memory-building is included), versus the 60-230s/call
directly measured pre-fix in the diagnosis logs -- consistent with the
fix, by any reading of the composition.

## Conclusion

The fix in [decisions/0016](../decisions/0016-disable-ollama-thinking-mode.md)
works end-to-end, not just on the isolated benchmark that motivated it --
a full 1,986-question, two-`k` sweep now completes and produces results
competitive with GPT-4o-mini on this benchmark. This closes out the
multi-week qwen3.5:9b slowness investigation.

Since this isn't a reproduction target, there's no "did it match the
paper" bar to clear here -- it's a successful demonstration that the
paper-reproduction pipeline (and its new logging/`think=False` fix) work
correctly against a model outside the paper's original six. Open
follow-ups, none started: capturing real wall-clock/cost numbers for this
model now that it's fast; deciding whether `qwen3.5:9b` is worth adding
as a GEPA `task_lm` candidate (PR #5) given its competitive showing here.
